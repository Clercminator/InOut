### Repeatable release enforcement

`npm run parity:check` runs in `npm run verify`, native CI jobs, the Pulse workflow and EAS pre-install. It checks shared identity/version, billing/ad profile modes, developer guards, consent defaults, and reviewed platform-specific source hashes in `release/parity.json`. Any change in a known native difference requires renewed equivalence review and its source hash; new platform routes fail. This intentionally does not prove arbitrary runtime behavior. The existing `nativeDeviceAcceptance` gate remains mandatory.

Both store artifacts require the same `INOUT_RELEASE_MANIFEST` file, provided privately as an EAS file variable in the chosen environment. Prepare it only after candidate approval:

1. Check Play **all tracks/drafts** and App Store Connect/TestFlight build history. Set the approved shared semantic version and independently greater build identifiers in `apps/mobile/app.json`; keep auto-increment disabled.
2. Commit the reviewed product changes, use a clean checkout and run `node scripts/check-parity.mjs --fingerprint`. Record that output and `git rev-parse HEAD`. No candidate manifest was fabricated for this unfinished release.
3. The manifest JSON has `sourceCommit` (full SHA), `sourceFingerprint` (64-character output), `version`, `profile` (`store-test` or `production`), and `android`/`ios` objects each containing `buildIdentifier`, `lastUploaded` and `historyEvidence` (dated store-history evidence reference). Keep this file outside tracked source so adding it does not change the frozen commit.
4. Provide both private Firebase file paths and the existing RevenueCat keys, then run `node scripts/check-parity.mjs --commercial --artifact-only` and `node scripts/check-parity.mjs --build` in that environment. Production artifact generation retains `INOUT_ARTIFACT_ONLY=1`; this never approves submission. EAS pre-install repeats the checks and compares a normalized fingerprint of actual source/assets/configuration to the manifest, catching dirty source uploaded under an old commit SHA.
5. Build Android and iOS from that same checkout/profile. The EAS success hook writes `apps/mobile/artifacts/release-receipt.json`; both build profiles retain it in supplemental build artifacts. Each receipt includes EAS build ID, commit, source fingerprint, semantic version, platform build identifier, profile and a hash of shared configuration plus public environment flags. Download and retain each receipt with its exact AAB/IPA.
6. Run `node scripts/check-parity.mjs --pair <android-receipt.json> <ios-receipt.json>` with the manifest/environment. Production `npm run release:check` additionally requires `INOUT_ANDROID_RECEIPT` and `INOUT_IOS_RECEIPT` and validates the pair. Missing/mismatched artifacts block release even after acceptance flags are approved. Successful receipt generation on EAS remains untested until the next native build.

The reviewed platform differences are native sharing, modal dismissal, haptics, Android blur interruption, date picker, notification channels, keyboard avoidance and store-specific billing/offer APIs. Their shared user-facing intent is recorded in `release/parity.json`; equivalent device behavior is still unaccepted. Firebase Remote Config is not used; product flags remain shared source. Source hashes enforce review, not automatic proof of equivalence.
